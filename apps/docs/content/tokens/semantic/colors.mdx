Semantic tokens are **intents**: `primary`, `foreground`,
`border`. Each theme fills those intents with different values,
and each mode (light / dark) brings its own mapping. This page is
the **truth table** for the seven bundled themes: Default, Claude,
ChatGPT, Gemini, Perplexity, Mistral and Purple.

## How to read the tables

- The **Light** and **Dark** columns render the exact declared
  value as a chip over that theme's own light or dark background,
  so both are faithful no matter which mode you are reading in.
- The **Value** columns show what the theme declares: a primitive
  name (an alias in the DTCG source, written to CSS as
  `var(--color-<token>)`) or, where the theme
  matches a product surface that has no primitive equivalent, a
  literal OKLCH value.
- A `base` badge means the theme does **not** override that token;
  it inherits the value from the base layer
  (`semantic/light.json` and `semantic/dark.json`). That
  inheritance is the shipped behavior, not an omission.

If you are auditing a component that looks "wrong" in some theme,
start here. Comparing the intent (e.g. `--primary`) with the value
it resolves to in each theme tells you whether the inconsistency
comes from the component chrome or from the theme mapping.

## About the sidebar tokens

The `--sidebar-*` tokens are a **parallel family** covering the
side navigation chrome. They exist because sidebars are surfaces
often painted differently from `background` (darker, lighter,
contrasting). Keeping dedicated intents avoids the "tinted
background" trick that breaks when the theme changes.

## About the chart tokens

`--chart-1` through `--chart-5` alias the categorical scale
(`--chart-cat-1..5`), which is not themeable: every theme shows the
same series colours. See [Chart tokens](/tokens/chart).

## Editing or adding themes

Themes are **override layers** on top of the base semantic layer. Their source
is DTCG JSON in `packages/tokens/tokens/themes/<id>.json`; the CSS in
`packages/tokens/styles/` is generated from it. The short recipe:

1. **Create** `packages/tokens/tokens/themes/<id>.json` with a `light` and a
   `dark` group, and add `<id>` to `THEMES` in `packages/tokens/pipeline/model.ts`.
2. **Override only what differs** from the base, as DTCG tokens: an alias names
   the token path (`{color.emerald.700}`); a literal is an OKLCH colour object.
   Whatever the light group declares as a literal colour, the dark group must
   declare again, because `:root[data-theme]` outranks `.dark`.
3. **Build** with `nx build tokens`. The theme gets its CSS file, its `@import`
   in `theme.css`, and its JSON, TypeScript, Kotlin and Swift outputs.
4. **Audit** with `nx test tokens`: the contrast test fails on any text pair
   under 4.5:1 and any focus ring under 3:1, unless the pair is listed in
   `contrast-deviations.json` with a reason.

<Callout type="warn">
  **Reach for primitives first.** Reference the ramps by alias
  (`{color.<ramp>.<step>}`) so a primitive edit cascades into every theme. The
  shipped themes hardcode OKLCH only where they match a product surface that
  has no primitive equivalent (e.g. the Claude cream background or the Gemini
  graphite). If your value is reusable, add it as a primitive instead.
</Callout>
